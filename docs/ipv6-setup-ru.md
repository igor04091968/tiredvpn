# Настройка IPv6 на сервере TiredVPN

Это руководство относится к Linux-выходному серверу TiredVPN и клиентам в режиме TUN, включая Android. В нём разделены два независимых вида IPv6: подключение клиента к серверу и передача IPv6-трафика клиента через туннель.

## Что именно настраивается

| Функция | Что делает | Настройка |
| --- | --- | --- |
| IPv6-транспорт | Подключает клиента к серверу по IPv6. | Серверный `-enable-v6` / `-listen-v6`; в Android — поле «Адрес IPv6» и предпочтение IPv6. |
| IPv6 в туннеле | Передаёт IPv6-трафик телефона через VPN и выводит его в интернет через сервер. | На выходном сервере — `-ip-pool-v6`; в Android — «IPv6 в туннеле (двойной стек)». |

IPv6-трафик внутри туннеля может работать и при подключении телефона к серверу по IPv4. Включение только IPv6-транспорта не включает IPv6-выход.

## Требования к выходному серверу

- Сервер TiredVPN работает в режиме TUN: задан `-ip-pool`, обычно `10.8.0.0/24`.
- Для IPv6-клиентов задан отдельный уникальный ULA-префикс `-ip-pool-v6` из диапазона `fc00::/7`. Для текущей реализации префикс должен быть `/96` или короче; обычный выбор — отдельный `/64`.
- У сервера есть рабочий IPv6-адрес и маршрут наружу. NAT66 не создаёт доступ к IPv6-интернету, если у самого сервера нет рабочего IPv6 uplink.
- Серверная версия поддерживает dual-stack TUN. Обновляйте выходные узлы и relay до подключения клиентов, которые запрашивают IPv6.

Например, добавьте к существующей команде запуска:

```sh
-ip-pool 10.8.0.0/24 \
-ip-pool-v6 fd00:10:8::/64
```

Префикс IPv6 должен быть уникальным для этого пула и не пересекаться с маршрутизируемыми сетями. Не используйте один и тот же пул для разных узлов, если они делят Redis и выдачу адресов.

### Установка через systemd

Сначала посмотрите фактический unit и сохраните все его текущие аргументы:

```sh
sudo systemctl cat tiredvpn
```

Для стандартного пакетного unit можно создать override командой `sudo systemctl edit tiredvpn`:

```ini
[Service]
Environment=TIREDVPN_IP_POOL_V6=fd00:10:8::/64
ExecStart=
ExecStart=/usr/bin/tiredvpn server -listen ${TIREDVPN_LISTEN} -cert ${TIREDVPN_CERT} -key ${TIREDVPN_KEY} -ip-pool ${TIREDVPN_IP_POOL} -ip-pool-v6 ${TIREDVPN_IP_POOL_V6}
```

При наличии Redis, GOST, API или других параметров сохраните их в новой строке `ExecStart`; пример выше показывает только стандартный пакетный unit. Не вставляйте секреты в override или командную строку: секрет остаётся в защищённом `EnvironmentFile`.

Примените изменение и перезапустите сервер в окно обслуживания — активные VPN-сессии оборвутся:

```sh
sudo systemctl daemon-reload
sudo systemctl restart tiredvpn
```

## Форвардинг, NAT66 и firewall

На Linux TiredVPN автоматически включает IPv6 forwarding и устанавливает собственные nftables-правила NAT66/MASQUERADE и forward accept для настроенного пула. Таблица создаётся при запуске сервера и относится только к этому пулу. При IPv6 uplink, полученном через Router Advertisement, сервер корректирует `accept_ra` WAN-интерфейса с `1` на `2`, чтобы маршрут не истёк после включения forwarding; значения `0` и `2` он оставляет без изменений.

Правила TiredVPN не могут отменить `drop` в другой базовой цепочке firewall. Если у системы есть собственная политика `FORWARD DROP`, firewall должен отдельно разрешать пересылку трафика между TUN-интерфейсом TiredVPN и WAN для IPv6-пула, а обратные соединения — в состоянии `ESTABLISHED,RELATED`. Вносите это правило в действующую систему firewall и сохраняйте её обычным способом. Не очищайте чужие таблицы nftables и не добавляйте вторую NAT66-конфигурацию поверх автоматической.

Откройте входящие TCP/UDP-порты, реально используемые настройками `-listen`, GOST или другого выбранного транспорта, по IPv6 на внешнем firewall и в локальной политике. Само наличие IPv6-listener не открывает порт в firewall.

## Проверка

На сервере:

```sh
systemctl is-active tiredvpn
ip -6 addr show dev tiredvpn0
cat /proc/sys/net/ipv6/conf/all/forwarding
nft list tables | grep tiredvpn-nat6
journalctl -u tiredvpn -b --no-pager | grep -E 'NAT66|dual-stack|IPv6 pool'
curl -6 https://api6.ipify.org
```

Для успешного dual-stack TUN журнал должен показывать IPv6-пул, создание NAT66 и выдачу клиенту адресов dual-stack. Последняя команда проверяет только IPv6-выход самого сервера; она не заменяет тест с телефона.

На телефоне подключитесь через TiredVPN и откройте [test-ipv6.com](https://test-ipv6.com). При исправном туннеле сайт покажет IPv4 и IPv6 адреса выхода сервера; мобильный адрес оператора не должен быть IPv6-адресом VPN-сеанса.

## Если IPv6 не работает

- **Виден IPv4 сервера, но test-ipv6.com пишет No IPv6:** проверьте включение клиентского переключателя «IPv6 в туннеле», dual-stack адрес в активном сеансе и то, что тестируемое приложение маршрутизируется через VPN.
- **IPv6-only сайты не открываются:** проверьте IPv6 default route сервера, появление `tiredvpn-nat6-*`, счётчики/состояние firewall и отсутствие внешнего `FORWARD DROP` без соответствующего разрешения.
- **В журнале есть подключение с IPv6-адреса телефона:** это подтверждает только IPv6-транспорт до сервера, но не IPv6 внутри TUN.
- **В журнале нет dual-stack выдачи:** клиент не запросил IPv6 либо подключён к старому exit/relay без `-ip-pool-v6`.

Настройка Android-клиента описана в [руководстве по IPv6 в приложении](https://github.com/igor04091968/tiredvpn-android/blob/main/docs/ipv6-ru.md).

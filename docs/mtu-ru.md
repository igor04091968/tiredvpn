# MTU IPv4 и IPv6

Начните с MTU 1280 на сервере и клиенте. Это значение по умолчанию и минимальный MTU IPv6-интерфейса. Оно не гарантирует проходимость любого внешнего канала: внешний транспорт отдельно отвечает за сегментацию, фрагментацию и свой PMTU.

Для одного TUN-интерфейса используется общий MTU обеих версий IP. Различается TCP MSS:

| MTU | MSS IPv4 | MSS IPv6 |
|---|---|---|
| 1280 | 1240 | 1220 |
| 1400 | 1360 | 1340 |
| 1500 | 1460 | 1440 |

Ядро вычитает фиксированные заголовки IP и TCP по [RFC 6691](https://www.rfc-editor.org/rfc/rfc6691.html). Ограничение применяется только к SYN/SYN-ACK и только уменьшает объявленный MSS. Меньшее значение от другого участника сохраняется и в программном пути, и в правилах nftables.

Программный путь поддерживает IPv6 с заголовками расширений. Настоящие фрагменты и IPsec-пакеты не переписываются; атомарный IPv6-фрагмент обрабатывается как полный пакет. Контрольная сумма TCP обновляется по [RFC 1624](https://www.rfc-editor.org/rfc/rfc1624.html), включая MSS с нечётным смещением в опциях.

## Настройки

Сервер принимает `-tun-mtu 1280` (диапазон 1280–9000). При регистрации клиента сервер ограничивает MSS меньшим из MTU клиента и сервера. Это действует в нативном TUN, Morph, Confusion, H2 и HTTP Polling. Старый клиент без значения MTU использует серверное значение.

Linux-клиент поддерживает `-auto-mtu`: проба идёт по установленному туннелю и не поднимает MTU выше `-tun-mtu`. У значения по умолчанию 1280 нет пространства для повышения. Проба подтверждает доставку туннельного кадра, а не измеряет физический PMTU внешней сети: потоковый транспорт может разбить кадр на несколько сетевых пакетов. Транспорты без поддержки проб сохраняют статическое значение.

На Android пустое поле MTU означает значение от ядра, обычно 1280. Это не фоновое измерение PMTU: интерфейс принадлежит VpnService. Настройка служит верхней границей, а MTU интерфейса не должен превышать значение ядра. Некорректные числа из импорта заменяются автоматическим режимом. JNI также проверяет число и диапазон. IPv6 внутри туннеля включается отдельной настройкой профиля.

## Слишком большие пакеты

TCP MSS не решает задачу UDP и остальных протоколов. Для слишком большого входящего пакета клиент возвращает уведомление исходному отправителю через туннель: ICMP Fragmentation Needed для IPv4 или ICMPv6 Packet Too Big, Type 2, для IPv6. Ошибки не подаются как входящий трафик в локальный TUN, поскольку их адресат находится на удалённой стороне.

IPv6-ошибка содержит MTU, цитату исходного пакета и контрольную сумму с псевдозаголовком; её полный размер не превышает 1280. Применяется ограничение частоты отдельно для каждого соединения: 10 ошибок в секунду с начальной серией до 10. Ответы на ICMP-ошибки и сообщения от неопределённого/многоадресного источника подавляются. Формат и ограничения описаны в [RFC 4443](https://www.rfc-editor.org/rfc/rfc4443.html), механизм PMTUD — в [RFC 8201](https://www.rfc-editor.org/rfc/rfc8201.html).

Внешние правила firewall должны пропускать необходимые ICMP/ICMPv6 сообщения. Изменения в коде не исправляют недоступный тестовый сервер или внешний маршрут.

## Как проверять повышение MTU

Повышайте верхнюю границу только после контрольного прогона: IPv4 и IPv6, загрузка и отдача большого файла, UDP, переподключение и смена Wi-Fi/мобильной сети. Сравнивайте одинаковые сервер, транспорт и доступный конечный узел. При зависании проверьте доставку ICMPv6 Type 2 и верните 1280. Тайм-аут соединения до TCP SYN-ACK сам по себе не доказывает проблему крупных пакетов.

Не выставляйте MTU 1500 всем устройствам по одному успешному веб-тесту. В этой правке сохранено 1280; рост пропускной способности на телефоне ещё не измерен.

## Проверка разработчиком

Обычные тесты: `go test ./internal/tun ./internal/server ./cmd/tiredvpn`. Дополнительно запускаются целевые тесты с `-race`. Тесты охватывают обе версии IP, контрольные суммы, заголовки расширений, PMTU для IPv6-фрагментов, возврат ошибок по туннелю, короткие/конкурентные записи и ограничения входного кадра.

`TestMTUNFTIsolatedNamespace` проверяет установку и чтение правил обеих семей реальным ядром. Он выключен по умолчанию. Для запуска соберите тестовый бинарник и выполните его с `TIREDVPN_MTU_NFT_TEST=1` от root внутри свежего `unshare --net`; тест откажется работать в сетевом пространстве PID 1. Не запускайте весь набор root-тестов в пространстве хоста.

Если каталог временной сборки на USB имеет длинный путь, соберите тестовый бинарник с `GOTMPDIR` на USB, затем выполните его из каталога пакета с `env -u GOTMPDIR TMPDIR=/tmp`. Это позволяет тестовым UNIX-сокетам уложиться в ограничение длины пути.

## Обновление ранних установок

В старых установках после нескольких перезапусков могли остаться безусловные правила MSS в таблицах `ip tiredvpn-tiredvpn0` и `ip6 tiredvpn-tiredvpn0`. Если они выполняются раньше новых правил, они повышают ранее уменьшенный MSS. Смена бинарника сама по себе не удаляет накопленное состояние ядра.

Перед первым переходом сохраните вывод `sudo nft -a list table ip tiredvpn-tiredvpn0` и такой же команды для `ip6`. В цепочке `mssclamping` должны остаться правила с условием `tcp option maxseg size > 1240` для IPv4 и `> 1220` для IPv6 при MTU 1280. Старые безусловные и повторяющиеся правила удаляются только в этих таблицах, по их `handle` из вывода nft. Общее `flush ruleset` для этого не требуется. Если nft-правила дополнительно восстанавливаются отдельной службой из файла, обновите и этот источник.

При штатной выкладке версии .8 на рабочие узлы старые цепочки были заменены одной транзакцией nft, без изменения остальных таблиц и перезапуска соседних VPN-служб. После обновления четыре транспорта передали данные на каждом сервере: REALITY, Single Flight, QUIC Salamander и ГОСТ. Проверка телефоном после установки нового APK остаётся отдельным шагом.
